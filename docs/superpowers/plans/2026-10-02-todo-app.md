# 할 일 관리 앱 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 의존성 없는 단일 `index.html` 하나로 동작하는 개인용 할 일 관리 웹앱을 만든다.

**Architecture:** 파일은 `index.html` 하나뿐이다. 그 안에서 STATE → STORAGE → LOGIC → RENDER → EVENTS → INIT 순서로 영역을 나누고, STORAGE와 LOGIC은 DOM을 절대 참조하지 않는다. LOGIC은 배열을 받아 새 배열을 돌려주는 순수 함수로 작성해 콘솔에서 단독 검증이 가능하게 한다. 화면은 상태가 바뀔 때마다 전체를 다시 그린다.

**Tech Stack:** HTML + CSS + 순수 JavaScript (ES2020). 빌드 도구·프레임워크·패키지 매니저 없음. 저장은 `localStorage`.

**Spec:** [docs/superpowers/specs/2026-10-02-todo-app-design.md](../specs/2026-10-02-todo-app-design.md)

## Global Constraints

모든 단계에 공통으로 적용된다. 각 단계의 요구사항에 이 절이 암묵적으로 포함된다.

- 파일은 `index.html` 하나다. CSS와 JS를 그 안에 인라인으로 둔다. 추가 파일을 만들지 않는다.
- 외부 의존성 0개. `package.json`, CDN 링크, 웹폰트, 분석 스크립트를 넣지 않는다.
- 외부 네트워크 요청 0건. 오프라인에서 동작해야 한다.
- `file://`에서 동작해야 한다. `<script type="module">`과 `import`/`export`를 쓰지 않는다.
- 사용자 입력은 `textContent`로만 삽입한다. `innerHTML` 사용 금지.
- STORAGE와 LOGIC 영역의 함수는 `document`, `window`, DOM API를 참조하지 않는다.
- UI 언어는 한국어.
- 카테고리는 `['업무', '개인', '공부']` 3종 고정. 사용자가 추가할 수 없다.
- localStorage 키는 `todo-app-v1`, 손상 백업 키는 `todo-app-v1.corrupt`, `SCHEMA_VERSION`은 `1`.
- 지원 최소 폭 360px. 이 폭에서 가로 스크롤이 생기지 않아야 한다.
- 대상 브라우저: Chrome / Edge / Firefox / Safari 최신.
- 항목 100개까지 체감 지연 없이 동작해야 한다.

## Review Focus

PRD가 함의하지만 어느 단계의 체크리스트도 직접 검증하지 않는 입력·상황 5가지다. 실제 사용 중 문제를 일으킬 가능성이 높은 순서로 적었고, 각 항목을 담당 단계에 테스트로 배정했다.

1. **인라인 편집 중 다른 항목을 조작하면 편집 내용이 날아간다.** 제목을 고치는 중에 다른 항목의 체크박스를 누르면 전체 재그리기가 일어나 입력 필드가 사라진다. 사용자는 편집 중이던 내용이 저장되거나 최소한 유지되기를 기대한다. → **4단계**
2. **되돌리기 대기 중 다른 조작을 하면 보관함이 꼬인다.** 삭제 후 5초 안에 다른 항목을 삭제하거나 새 항목을 추가했을 때, 되돌리기가 엉뚱한 항목을 복구하거나 이미 만료된 타이머가 나중에 발동해서는 안 된다. → **4단계**
3. **같은 앱을 두 탭에 열어두면 한쪽 변경이 다른 쪽에 덮어써진다.** PRD가 다루지 않은 상황이다. 사용자는 한 탭에서 추가한 항목이 다른 탭에서 사라지기를 기대하지 않는다. → **1단계**
4. **카테고리 값이 3종 목록에 없는 데이터가 저장되어 있으면 진행률 합이 어긋난다.** 전체 진행률에는 잡히지만 카테고리별 3줄 어디에도 속하지 않아 FR-7의 "합 일치"가 깨진다. → **1단계**
5. **공백 없는 매우 긴 문자열(URL 등)은 말줄임이 걸리지 않고 레이아웃을 밀어낸다.** T-26의 "긴 제목"과 다른 입력 종류다. → **3단계**

## 1단계: 골격과 저장 계층

**Files:** Create `index.html`

**Interfaces — Produces:**
```js
const STORAGE_KEY = 'todo-app-v1';
const CORRUPT_KEY = 'todo-app-v1.corrupt';
const SCHEMA_VERSION = 1;
const CATEGORIES = ['업무', '개인', '공부'];

// Todo = { id: string, title: string, category: string, done: boolean, createdAt: number }

loadState() -> { todos: Todo[], mode: 'persistent'|'memory', error: null|'corrupt'|'blocked' }
saveState(todos: Todo[]) -> { ok: boolean, error: null|'quota'|'blocked' }
isValidTodo(value: unknown) -> boolean
showBanner(message: string, kind: 'warn'|'error') -> void
```

### 붙여넣을 프롬프트

```
docs/superpowers/specs/2026-10-02-todo-app-design.md 를 읽고, 그 PRD의 1단계를
구현해줘. 이 단계의 목표는 "빈 화면이 뜨고, 데이터가 안전하게 보존되는 토대"야.
아직 할 일을 추가하는 기능은 만들지 않아.

제약 (반드시 지킬 것):
- 파일은 index.html 하나만 만든다. CSS와 JS를 인라인으로 넣는다.
- 외부 의존성, CDN, 웹폰트, 네트워크 요청 0개.
- <script type="module">과 import/export 금지. file:// 에서 열려야 한다.
- STORAGE 영역 함수는 document/window/DOM을 참조하지 않는다.
- 사용자 입력은 textContent로만 삽입한다. innerHTML 금지.

만들 것:

1. HTML 골격 — PRD 8절 레이아웃의 빈 껍데기만.
   제목 / 입력 영역 / 진행률 영역 / 필터 영역 / 목록 <ul> / 배너 영역 / 토스트 영역.
   목록 <ul>은 비워둔다. 입력과 필터는 보이기만 하고 아직 동작하지 않아도 된다.

2. CSS — 디자인 토큰(색/간격/폰트)을 :root에 먼저 정의하고, 그다음 레이아웃,
   그다음 컴포넌트 순서로. 최대 본문 폭을 두고 가운데 정렬. 최소 폭 360px에서
   가로 스크롤이 없어야 한다.

3. JS 영역을 PRD 10절 순서로 주석으로 구획한다:
   [1] STATE / [2] STORAGE / [3] LOGIC / [4] RENDER / [5] EVENTS / [6] INIT
   이번 단계에서는 [1] [2] [6]만 채운다. 나머지는 주석만 남겨둔다.

4. [1] STATE:
   let todos = [];
   let filter = { status: 'active', category: 'all' };
   let lastDeleted = null;
   let storageMode = 'persistent';

5. [2] STORAGE — 아래 시그니처 그대로:
   const STORAGE_KEY = 'todo-app-v1';
   const CORRUPT_KEY = 'todo-app-v1.corrupt';
   const SCHEMA_VERSION = 1;
   const CATEGORIES = ['업무', '개인', '공부'];

   isValidTodo(value) -> boolean
     id가 비어있지 않은 문자열, title이 비어있지 않은 문자열,
     category가 CATEGORIES에 포함, done이 boolean, createdAt이 유한한 숫자.
     하나라도 어긋나면 false.

   loadState() -> { todos, mode, error }
     - 키가 없으면 { todos: [], mode: 'persistent', error: null }
     - JSON 파싱 실패 / 최상위가 객체가 아님 / todos가 배열이 아님 /
       항목 중 isValidTodo를 통과하지 못하는 것이 하나라도 있음
       → 원본 문자열을 CORRUPT_KEY로 옮기고 원래 키를 지운 뒤
         { todos: [], mode: 'persistent', error: 'corrupt' }
     - localStorage 접근 자체가 예외를 던지면
       { todos: [], mode: 'memory', error: 'blocked' }

   saveState(todos) -> { ok, error }
     { version: SCHEMA_VERSION, todos } 를 JSON으로 저장.
     QuotaExceededError → { ok: false, error: 'quota' }
     접근 차단 → { ok: false, error: 'blocked' }
     storageMode가 'memory'면 저장을 시도하지 않고 { ok: true, error: null }.

6. [6] INIT — loadState()를 호출해 todos와 storageMode를 채우고,
   error에 따라 배너를 띄운다. showBanner(message, kind)를 만들어라.
     'corrupt' → "저장된 데이터를 읽을 수 없어 새로 시작합니다" (kind 'error')
     'blocked' → "이 창을 닫으면 데이터가 사라집니다" (kind 'warn', 계속 표시)
   todos가 비어 있으면 목록 자리에 "첫 할 일을 추가해보세요"를 표시한다.
   진행률 영역은 0/0 0%와 빈 바로 표시한다. NaN이 절대 보이면 안 된다.

7. 다른 탭과의 충돌 방지 (PRD에 없던 항목, Review Focus 3):
   window에 'storage' 이벤트 리스너를 달고, event.key가 STORAGE_KEY일 때
   loadState()로 다시 읽어 todos를 갱신한다. 두 탭을 열어두었을 때
   한쪽 변경이 다른 쪽에 조용히 덮어써지지 않게 하는 최소 장치다.

8. 디버깅용으로 window.__app = { loadState, saveState, isValidTodo } 를 노출한다.

검증 — 브라우저에서 index.html을 직접 열고 아래를 순서대로 확인하고 결과를 보고해줘:
  T-01  데이터 없이 첫 실행 → 안내 문구, 진행률 0/0 0%, 빈 바, NaN 없음
  T-23  콘솔에서 localStorage.setItem('todo-app-v1', '{깨진') 후 새로고침
        → 'corrupt' 배너, 빈 상태, todo-app-v1.corrupt 키 생성 확인
  R-04  콘솔에서 category가 '운동'인 항목을 넣어 저장 후 새로고침
        → 유효하지 않은 항목이므로 corrupt로 처리되고 .corrupt에 원본 보존
  T-24  시크릿 창에서 열기 → 'blocked' 경고 배너, 화면은 정상 렌더
  R-03  같은 파일을 두 탭에 열고, 한 탭 콘솔에서 saveState로 값을 바꾼 뒤
        → 다른 탭이 storage 이벤트로 갱신되는지 확인
  T-19/T-20 은 아직 추가 기능이 없으므로 콘솔에서 saveState로 직접 심은 뒤
        새로고침·브라우저 재시작으로 복원되는지 확인

검증이 모두 통과하면 커밋:

  git commit -m "feat: 앱 골격과 localStorage 저장 계층 구현"
```

## 2단계: 로직 계층

**Files:** Modify `index.html` (`[3] LOGIC` 영역)

**Interfaces — Consumes:** 1단계의 `CATEGORIES`만. `saveState`를 호출하지 않는다 — 저장은 4단계의 `commit()`이 담당한다.
**Interfaces — Produces:** 모두 순수 함수. 입력 배열을 변경하지 않고 새 배열을 돌려준다.
```js
createTodo(title: string, category: string) -> Todo | null
addTodo(list: Todo[], title: string, category: string) -> Todo[]
updateTitle(list: Todo[], id: string, title: string) -> Todo[]
updateCategory(list: Todo[], id: string, category: string) -> Todo[]
toggleDone(list: Todo[], id: string) -> Todo[]
removeTodo(list: Todo[], id: string) -> { list: Todo[], removed: Todo|null, index: number }
restoreTodo(list: Todo[], todo: Todo, index: number) -> Todo[]
filterTodos(list: Todo[], filter: {status, category}) -> Todo[]
calcProgress(list: Todo[], category?: string) -> { done: number, total: number, percent: number }
```

### 붙여넣을 프롬프트

```
index.html 의 [3] LOGIC 영역을 구현해줘. 이 단계는 화면을 전혀 건드리지 않는다.
모든 함수는 순수 함수이고, DOM(document/window)을 참조하면 안 된다.
이 규칙이 "계산이 틀렸는지 표시가 틀렸는지" 구분하는 유일한 수단이다.

입력 배열을 변경(mutate)하지 말고 새 배열을 반환해라.

구현할 시그니처:

createTodo(title, category) -> Todo | null
  title을 trim한다. 빈 문자열이면 null을 반환한다 (던지지 않는다).
  category가 CATEGORIES에 없으면 null.
  id는 Date.now() + '-' + 랜덤문자열. 같은 밀리초에 두 번 호출해도 충돌하지 않아야 한다.
  createdAt은 Date.now(). done은 false.

addTodo(list, title, category) -> Todo[]
  createTodo가 null이면 list를 그대로 반환한다. 아니면 맨 뒤에 붙인 새 배열.

updateTitle(list, id, title) -> Todo[]
  trim 결과가 빈 문자열이면 list를 그대로 반환한다. 삭제하지 않는다 (FR-2).

updateCategory(list, id, category) -> Todo[]
  category가 CATEGORIES에 없으면 list를 그대로 반환한다.

toggleDone(list, id) -> Todo[]
  해당 항목의 done을 반전한다.

removeTodo(list, id) -> { list, removed, index }
  삭제한 항목과 그 인덱스를 함께 반환한다. 되돌리기에 필요하다.
  id가 없으면 { list, removed: null, index: -1 }.

restoreTodo(list, todo, index) -> Todo[]
  index 위치에 todo를 다시 끼워넣는다. index가 범위를 벗어나면 맨 뒤에 붙인다.

filterTodos(list, filter) -> Todo[]
  filter.status: 'all' | 'active' | 'done'   ('active'는 done === false)
  filter.category: 'all' | '업무' | '개인' | '공부'
  두 축은 독립적으로 AND 결합된다.
  정렬하지 않는다. 입력 순서(추가된 순서)를 유지한다.

calcProgress(list, category) -> { done, total, percent }
  category를 생략하거나 'all'이면 전체 기준.
  percent는 Math.round(done / total * 100). total이 0이면 percent도 0.
  NaN이나 Infinity를 반환해서는 안 된다.

window.__app 에 위 함수 전부를 추가로 노출해라. 이 단계의 검증 수단이다.

검증 — 브라우저 콘솔에서 아래를 직접 실행하고 결과를 보고해줘:
  const A = window.__app;
  1. A.createTodo('   ', '업무') === null
  2. A.createTodo('x', '운동') === null
  3. 같은 틱에 createTodo를 2번 호출 → id가 서로 다름
  4. let L = []; L = A.addTodo(L, '보고서', '업무'); L = A.addTodo(L, '장보기', '개인');
     L = A.addTodo(L, '알고리즘', '공부'); L.length === 3
  5. 원본 불변 확인: const before = L; A.addTodo(L, 'x', '업무'); before.length === 3
  6. A.updateTitle(L, L[0].id, '  ') 가 제목을 지우지 않고 L과 동일한 내용인지
  7. T-16  일부 done 처리 후 calcProgress(L) 의 done/total/percent가 실제와 일치
  8. T-17  calcProgress(L,'업무').total + calcProgress(L,'개인').total
           + calcProgress(L,'공부').total === calcProgress(L).total
           (done 합도 동일하게 일치)
  9. calcProgress([]) 가 { done: 0, total: 0, percent: 0 } 이고 NaN이 없음
 10. filterTodos(L, {status:'active', category:'공부'}) 가 교차 조건으로 동작
 11. const r = A.removeTodo(L, L[1].id); A.restoreTodo(r.list, r.removed, r.index)
     → 원래 순서가 그대로 복원됨

검증이 모두 통과하면 커밋:
  git add index.html
  git commit -m "feat: 할 일 CRUD와 진행률 계산 로직 구현"
```

## 3단계: 렌더링

**Files:** Modify `index.html` (`[4] RENDER` 영역 + CSS)

**Interfaces — Consumes:** 2단계의 `filterTodos`, `calcProgress`, `CATEGORIES`
**Interfaces — Produces:**
```js
render() -> void                               // 전체 재그리기. 상태를 읽어 화면 전부를 갱신
renderProgress(list: Todo[]) -> void
renderList(list: Todo[], filter) -> void
renderFilters(filter) -> void
emptyMessage(filter) -> string                 // 순수 함수. 필터 조건에 맞는 안내 문구
```

### 붙여넣을 프롬프트

```
index.html 의 [4] RENDER 영역을 구현해줘. 아직 이벤트는 붙이지 않는다.
이번 단계가 끝나면 콘솔에서 todos 배열을 바꾸고 render()를 부르면
화면이 올바르게 그려져야 한다.

원칙:
- 전체 재그리기로 구현한다. 20개 규모에서 부분 갱신은 과설계다.
- 모든 사용자 입력 텍스트는 textContent로만 넣는다. innerHTML 금지.
- 진행률은 PRD D-3에 따라 "필터와 무관하게 항상 전체 데이터 기준"으로 계산한다.
  filterTodos를 거친 배열을 calcProgress에 넘기면 안 된다. 이걸 틀리기 쉽다.

구현할 것:

render() -> void
  renderProgress(todos), renderList(todos, filter), renderFilters(filter) 를 호출한다.
  외부에서 상태를 바꾼 뒤 이 함수 하나만 부르면 화면이 맞아야 한다.

renderProgress(list) -> void
  전체: 진행 바 + "완료수/전체수" + 백분율 정수.
  카테고리별: 업무/개인/공부 각각 짧은 바 + "완료수/전체수".
  calcProgress(list)와 calcProgress(list, 카테고리)를 쓴다.
  total이 0이면 "0/0 0%"와 빈 바. NaN/Infinity가 화면에 보이면 안 된다.
  진행 바에는 반드시 텍스트 수치를 함께 표시한다 (접근성).

renderList(list, filter) -> void
  filterTodos(list, filter) 결과를 <li>로 그린다. 각 행의 구성:
    - <input type="checkbox">  네이티브 요소를 쓴다. 가짜 체크박스 금지.
    - 제목 텍스트 (완료 항목은 취소선 + 흐리게)
    - 카테고리 배지 — 색으로 구분하되 글자(업무/개인/공부)를 항상 함께 표시한다.
      색만으로 구분하지 않는다.
    - 삭제 버튼
  각 <li>에 data-id 로 todo.id 를 넣어라. 4단계의 이벤트 위임이 이걸 쓴다.
  결과가 0건이면 emptyMessage(filter) 문구를 표시한다.

emptyMessage(filter) -> string
  순수 함수. DOM을 건드리지 않고 문자열만 반환한다.
  예: {status:'active', category:'공부'} → "진행중인 공부 할 일이 없습니다"
      {status:'all', category:'all'} → "첫 할 일을 추가해보세요"
  모든 status × category 조합에서 자연스러운 한국어가 나와야 한다.

renderFilters(filter) -> void
  상태 축(전체/진행중/완료)과 카테고리 축(전체/업무/개인/공부)의
  현재 선택 상태를 시각적으로 표시한다. 클릭 동작은 4단계에서 붙인다.

CSS 추가:
  - 완료 항목: 취소선 + 낮은 명도
  - 카테고리 배지 3색
  - 긴 제목: 최대 2줄 표시 후 말줄임
  - Review Focus 5: 공백 없는 긴 문자열(URL 등)도 레이아웃을 밀어내지 않도록
    overflow-wrap: anywhere (또는 word-break)를 함께 적용한다.
    말줄임 처리만으로는 이 입력이 막히지 않는다.
  - 최소 폭 360px에서 가로 스크롤 없음. 카테고리별 진행률 3줄은 좁은 폭에서
    세로로 쌓인다.

window.__app 에 render, emptyMessage 를 추가 노출해라.

검증 — 콘솔에서 todos를 직접 채우고 render()를 부른 뒤 확인하고 보고해줘:
  T-06  업무/개인/공부 각각 1개 이상 → 배지 색과 글자가 모두 올바름
  T-16  전체 진행률 숫자와 백분율이 실제 목록과 일치
  T-17  카테고리별 3줄의 완료수 합·전체수 합이 전체와 일치
  T-18  filter를 여러 조합으로 바꿔가며 render() → 진행률 숫자가 전혀 변하지 않음
        (D-3. 이게 틀리면 filterTodos 결과를 calcProgress에 넘긴 것이다)
  T-22  결과 0건이 되는 필터 조합 여러 개 → 조건에 맞는 자연스러운 문구가 나옴
  T-25  제목이 <img src=x onerror=alert(1)> 인 항목 → 문자로 그대로 보이고
        스크립트가 실행되지 않음
```

## 4단계: 상호작용

**Files:** Modify `index.html` (`[5] EVENTS` 영역, `[1] STATE`에 `editingId` 추가)

**Interfaces — Consumes:** 2단계 LOGIC 전체, 3단계 `render`
**Interfaces — Produces:**
```js
initEvents() -> void
commit(nextTodos: Todo[]) -> void   // 상태 교체 + saveState + render 를 한 곳에서 처리
beginEdit(id: string) -> void
commitEdit(id: string, value: string) -> void
cancelEdit() -> void
showUndoToast() -> void
hideUndoToast() -> void
```

### 붙여넣을 프롬프트

```
index.html 의 [5] EVENTS 영역을 구현해줘. 이번 단계가 끝나면 앱이 실제로 쓸 수 있어야 한다.

핵심 패턴 — 모든 상태 변경은 이 함수 하나를 거친다:
  commit(nextTodos)
    todos = nextTodos; saveState(todos) 결과가 실패면 배너로 알리되
    화면의 변경은 되돌리지 않는다(PRD 11절); 그리고 render().
  이렇게 하면 "저장 빠뜨림" 버그가 구조적으로 안 생긴다.

구현할 것:

1. 추가 (FR-1)
   입력창 Enter 와 추가 버튼 모두 동작.
   commit(addTodo(todos, 입력값, 선택된카테고리)).
   addTodo가 빈 제목을 걸러 list를 그대로 반환하므로, 추가 실패를 감지해
   입력창을 짧게 흔들고 포커스를 유지한다. alert을 쓰지 않는다.
   성공 시 입력창만 비우고 카테고리 선택은 유지한다. 포커스도 입력창에 유지한다.

2. 완료 토글 (FR-5)
   목록의 체크박스 change 를 <ul> 한 곳에서 이벤트 위임으로 처리한다.
   행마다 리스너를 붙이지 않는다. data-id로 대상을 찾는다.
   commit(toggleDone(todos, id)).

3. 제목 인라인 편집 (FR-2)
   제목 클릭 → 그 자리를 input으로 바꾸고 기존 제목을 채운 뒤 전체 선택.
   Enter 또는 blur → commitEdit(id, value). Esc → cancelEdit().
   값이 빈 문자열이면 updateTitle이 list를 그대로 반환하므로 자동으로 취소가 된다.
   삭제되지 않는 것을 반드시 확인해라.

   ** Review Focus 1 — 이 부분을 특히 조심해라 **
   [1] STATE 에 let editingId = null; 을 추가한다.
   render()가 전체 재그리기이므로, 편집 중에 다른 항목을 체크하면
   입력 필드가 날아가고 입력 중이던 내용이 사라진다.
   대책: editingId가 설정되어 있으면 render() 후에 해당 행을 다시 편집 상태로
   복원하고, 편집 중이던 입력값과 커서 위치를 유지한다.
   (또는 재그리기 전에 현재 편집값을 commitEdit로 확정한다. 어느 쪽이든
   "입력 중이던 내용이 조용히 사라지지 않는다"를 만족하면 된다. 선택한 방식을
   주석으로 한 줄 적어라.)

4. 카테고리 변경 (FR-3)
   배지 클릭 → 세 카테고리를 나열한 작은 드롭다운을 연다.
   하나 선택 → commit(updateCategory(todos, id, category)).
   클릭할 때마다 다음 값으로 순환하는 방식은 쓰지 않는다 (PRD FR-3).
   드롭다운이 열린 상태에서 재그리기가 일어나면 드롭다운을 닫는다.

5. 삭제와 되돌리기 (FR-4)
   삭제 버튼 → confirm 없이 즉시 제거.
     const r = removeTodo(todos, id);
     lastDeleted = { todo: r.removed, index: r.index };
     commit(r.list); showUndoToast();
   토스트는 "삭제됨 · 되돌리기"를 5초간 표시.
   되돌리기 클릭 → commit(restoreTodo(todos, lastDeleted.todo, lastDeleted.index));
                   lastDeleted = null; hideUndoToast();
   5초 경과 → hideUndoToast(); lastDeleted = null;

   ** Review Focus 2 — 타이머를 반드시 관리해라 **
   setTimeout 핸들을 변수에 보관하고, 새 삭제가 일어나면
   이전 타이머를 clearTimeout 한 뒤 새로 건다.
   요구사항은 "가장 최근 삭제 1건만 되돌릴 수 있다"(FR-4)이므로,
   연속 삭제 시 lastDeleted는 최신 것으로 덮어쓴다.
   이미 만료된 타이머가 나중에 발동해 엉뚱한 항목을 복구하거나
   새 토스트를 지워버리는 일이 없어야 한다.

6. 필터 (FR-6)
   상태 축과 카테고리 축을 독립적으로 바꾼다.
   filter를 갱신하고 render()만 부른다. saveState를 부르지 않는다 —
   필터 상태는 저장하지 않는 것이 PRD 6절의 결정이다.

7. 키보드 접근성
   추가·완료·수정·삭제를 키보드만으로 완주할 수 있어야 한다.
   체크박스와 버튼은 네이티브 요소이므로 기본 동작을 깨지 말아라.

8. [6] INIT 에서 initEvents()와 첫 render()를 호출한다.

검증 — 실제로 앱을 조작하며 확인하고 보고해줘:
  T-02  제목 입력 후 Enter → 맨 아래 추가, 입력창 비워짐, 포커스 유지
  T-03  추가 버튼으로도 동일

  T-07  체크 → 취소선, 기본 필터(진행중)에서 사라짐
  T-08  '완료' 필터에서 체크 해제 → 진행중으로 복귀

  T-10  수정 중 Esc → 원래 제목 유지
  T-11  수정 중 전부 지우고 Enter → 취소 처리, 삭제되지 않음
  T-12  배지로 카테고리 변경 → 출발·도착 카테고리 진행률 모두 갱신

  T-21  진행중 + 공부 조합 필터 동작
  R-01  제목 편집 중에 다른 항목의 체크박스 클릭
        → 편집 중이던 내용이 조용히 사라지지 않음
  R-02  항목 A 삭제 → 2초 뒤 항목 B 삭제 → 되돌리기
        → B가 복구되고, A의 만료 타이머가 토스트를 지우거나 A를 복구하지 않음
  키보드만으로 추가 → 체크 → 수정 → 삭제 완주

검증이 모두 통과하면 커밋:
```

## 부록: 단계 간 의존 관계

```
1단계 (STATE/STORAGE/INIT)
   └─> 2단계 (LOGIC)        — 1단계의 CATEGORIES 사용
          └─> 3단계 (RENDER) — 2단계의 filterTodos, calcProgress 사용
                 └─> 4단계 (EVENTS) — 2·3단계 전부 사용
                        └─> 5단계 (마감)
```

순차 실행이 필요하다. 병렬화할 수 있는 단계는 없다. 각 단계는 앞 단계의 Interfaces 블록에 적힌 이름과 시그니처를 그대로 쓴다.
